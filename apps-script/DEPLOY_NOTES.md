# Time4Med — คู่มืออัปเดต Apps Script หลังแก้ GitHub

ปรับปรุง 3 พฤศจิกายน 2026 — เว็บไซต์หลักยังคงเป็น GitHub Pages:
https://n4-p4t.github.io/Time4Med/test-v021/

## ข้อเท็จจริงที่ต้องแยกให้ชัด

- การ commit ไฟล์ `apps-script/Code.gs` หรือ `apps-script/Bridge.html` ลง GitHub **ไม่ได้อัปเดต Google Apps Script Web App** ที่ Deploy อยู่
- ฝั่งหน้าเว็บมีการตรวจ `capabilities` ของ backend: ถ้ายังไม่รองรับ จะไม่เปิดปุ่มใหม่ของ ADMIN เพื่อลดข้อผิดพลาด
- ห้ามแก้ Apps Script deployment URL ใน `test-v021/gas-only.js` โดยไม่จำเป็น
- ห้ามนำ `DEVICE_API_KEY`, `LINE_CHANNEL_ACCESS_TOKEN`, รหัสผ่าน หรือไฟล์ Secret ไปวางใน GitHub

## ขั้นตอน Deploy เมื่อพร้อมทดสอบหลังบ้าน

1. เปิดโปรเจกต์ Google Apps Script ตัวที่ใช้กับ Time4Med_DB ผ่านบัญชีที่เป็นเจ้าของ deployment
2. สำรองเวอร์ชันล่าสุดของ `Code.gs` และ `Bridge.html` ใน Apps Script ปัจจุบัน
3. นำ **เนื้อหาเต็ม** ของ `apps-script/Code.gs` และ `apps-script/Bridge.html` จาก commit ที่ผ่านการทดสอบแล้วไปอัปเดตในไฟล์ชื่อเดิม อย่าลบ Script Properties หรือ Triggers
4. ใน Apps Script ใช้ **Deploy → Manage deployments → Edit → New version → Deploy** เพื่อรักษา Web App URL เดิม (และให้สิทธิ์อนุญาตตามที่ Apps Script ถาม ถ้ามี)
5. กลับไปหน้า GitHub Pages กดรีเฟรชแล้วเข้า ADMIN; ควรเห็น `Apps Script: 2026-11-03-readiness-1` และเมนู LINE ที่รองรับ
6. กด **ตรวจความพร้อมล่าสุด** ในหน้า ADMIN เพื่อดูตารางยาจริง, ESP32-S3, การยืนยันซิงก์, กล้อง, LINE และโฟลเดอร์ Drive (แบบอ่านอย่างเดียว) จากนั้นกด **ตรวจความพร้อม LINE** เพื่อดูรายละเอียดผู้รับ ไม่มีการส่งข้อความหรือเปิด Trigger
7. ถ้าต้องทดสอบ LINE จริง ให้ใช้ปุ่มทดสอบข้อความเดิมและตรวจการรับข้อความที่โทรศัพท์ปลายทางอีกครั้ง

## ตรวจความพร้อมซอฟต์แวร์ (ADMIN)

- ฟังก์ชันใหม่ `getSystemReadiness(token)` เป็นแบบอ่านอย่างเดียวและใช้ `session_` + `needAdmin_` ตรวจสิทธิ์ฝั่ง Apps Script จริง
- หน้า ADMIN จะแสดงปุ่มเฉพาะเมื่อ backend ตอบ `capabilities.systemReadiness=true` เท่านั้น
- รายงานแยกสถานะ **ยาตารางจริง** ออกจากรายการ `TEST_/DEMO_/LINECHECK_` เพื่อไม่เปิดระบบด้วยข้อมูลจำลอง
- นำสถานะการเชื่อมต่ออุปกรณ์จาก Heartbeat ใหม่และการยืนยันตาราง (schedule hash + boot ID) มาแสดง แต่ไม่รับรอง LED/เสียง/กลอนว่าผ่าน
- รายงานว่าได้ตั้งค่า LINE token/trigger/recipient/IMAGE_FOLDER_ID แล้วหรือยัง โดยไม่แสดง token, LINE ID หรือ Drive folder ID จริง
- หากยังมีแต่ข้อมูลทดสอบหรืออุปกรณ์ยังไม่ตอบ `scheduleApplied` รายงาน **ไม่พร้อม** ตามจริงและไม่แตะข้อมูลใน Google Sheets

## การตั้งค่า LINE

- ฟังก์ชันใหม่: `getLineReadiness(token)` (ADMIN อ่านสถานะ) และ `saveLineRecipient(token, input)` (ADMIN ปรับผู้รับทีละคน)
- `saveLineRecipient` รับ LINE User ID ใหม่ได้ แต่ไม่ส่งค่าเดิมกลับไปยังเบราว์เซอร์; เก็บรหัสเดิมเมื่อเว้นช่องว่าง และลบได้เฉพาะเมื่อปิดการรับแจ้งเตือน
- การเปิดรับข้อความของบัญชี **ไม่เปิด** `LINE_REMINDERS_ENABLED` และ **ไม่สร้าง** trigger
- การเปิดใช้งานการแจ้งเตือนตามรอบยาจริงต้องตรวจค่า Script Properties, project trigger, ผู้รับ และรายการยาเข้าเงื่อนไขพร้อมกัน
- ฟังก์ชัน `inspectLineReminderReadiness()` สำหรับเจ้าของโปรเจกต์ใน editor เป็นแบบอ่านอย่างเดียว; แก้ข้อผิดพลาดการอ่านอีเมลใน revision นี้แล้ว

## ส่วนทดสอบ ADMIN

- `Bridge.html` เวอร์ชันใหม่อนุญาต `startDemo`, `getDemoStatus`, `cancelDemo`, `getDemoPreview`
- เมนูสาธิตบน GitHub Pages จะแสดงปุ่มจริงเฉพาะ backend ที่ตอบ `capabilities.demoAdmin`
- การมีปุ่ม **ไม่ใช่** หลักฐานว่าตู้ ESP32-S3 รองรับ `demoPoll/demoEvent`; ต้องตรวจร่วมกับฮาร์ดแวร์ก่อนรับรองผล

## การส่ง LINE เมื่อ Trigger ทำงานช้า

- ตัวส่ง `scheduledLineReminders_` ตรวจรอบยาที่ถึงเวลาใน **4 นาทีที่ผ่านมา** (รวมเวลานาทีปัจจุบัน) ตามเวลาไทย แทนการตรวจเพียงนาทีเดียว เพื่อรองรับ Trigger ที่ถูกเรียกคลาดเคลื่อน
- ใช้ **วันที่ของรอบยาจริง** แม้ Trigger จะข้ามเที่ยงคืนไปแล้ว
- บันทึก `notification_id` ก่อนยิง LINE และตรวจคีย์ใน `NotificationLog` เพื่อป้องกันการส่งซ้ำ หาก LINE ตอบผิดพลาดจะแสดง `FAILED` และไม่ส่งซ้ำโดยอัตโนมัติเพราะอาจทำให้ผู้ดูแลได้รับซ้ำ
- หาก Trigger หยุดนานเกิน 4 นาที รอบยาที่พลาดไปจะ **ไม่ถูกส่งย้อนหลัง** โดยอัตโนมัติ ต้องตรวจ Trigger, Logs และการตั้งค่าตามจริง
- การทดสอบที่ผ่านใน GitHub เป็นเพียงการจำลองเวลา/ข้อมูล ไม่ใช่การยืนยันว่า LINE จริงส่งตามเวลาบน Apps Script deployment ใหม่แล้ว

## ความถูกต้องของประวัติการกดยืนยัน (IntakeLog)

- อุปกรณ์ที่ส่งเหตุการณ์ `intake` โดยมีเพียง `patientId` จะบันทึก `confirmed_at` เป็นเวลาที่ได้รับข้อมูลจริง
- ถ้ายังไม่รู้ว่าเหตุการณ์นั้นเป็นรอบยาชนิดใดและกำหนดเวลาใด จะปล่อย `scheduled_at` ว่าง **ไม่เติมเป็นเวลาปัจจุบัน** เพราะจะทำให้คำนวณความตรงเวลาอย่างผิดความหมาย
- `IntakeLog.event_id` จะอ้างถึง `ActivityLog.event_id` ของเหตุการณ์เดียวกัน และแสดง `device_id` ของผู้รายงานตามจริง
- ฟังก์ชันนี้ยังไม่แปลว่า **ผู้สูงอายุกลืนยาแล้ว** หรือว่า **รับยาตรงเวลา** ต้องมีหลักฐานรอบยาที่ผูกกับรายการยาจริงก่อนจึงจะคำนวณสถิติการรับยาตรงเวลาได้
- เทสต์ซอฟต์แวร์แบบไม่แตะอุปกรณ์: `node tests/intake-audit-integrity.cjs`

## การยืนยันตารางยารุ่นล่าสุด (S3 schedule acknowledgment)

- `pullSchedule` ตอบกลับ `scheduleHash` (SHA-256 แบบ canonical) และ `scheduleCount` เพิ่มจาก `schedules` ที่มีอยู่แล้ว เพื่อไม่ทำลายความเข้ากันได้กับเฟิร์มแวร์เดิม
- เฟิร์มแวร์รุ่นใหม่ต้องใส่ `bootId` และส่ง `scheduleApplied:true`, `scheduleHash`, `scheduleCount` ใน Heartbeat **หลังนำตารางไปใช้จริงเท่านั้น**
- Backend จะเพิ่มหัวคอลัมน์ที่จำเป็นในชีต Devices เมื่อมี `bootId` ครั้งแรก และจะไม่รับรอง Sync จาก Heartbeat ปกติ
- ต้องทดสอบทั้งตารางมีรายการ / ตารางว่าง `[]` / เปลี่ยนยา / ปิดยา / รีสตาร์ตตู้ โดยใช้เอกสาร <https://github.com/N4-P4T/Time4Med/blob/main/docs/S3_SCHEDULE_SYNC_PROTOCOL_TH.md>
- เฟิร์มแวร์ปัจจุบันยังไม่ได้ส่งหลักฐานแบบใหม่ จึงคาดว่าเว็บไซต์จะยังแสดง “ยังไม่ยืนยัน” แม้ตู้ส่ง Heartbeat อยู่

## ข้อจำกัดที่ยังต้องแก้ในฮาร์ดแวร์และระบบร่วมกัน

- `pullSchedule` ส่งข้อมูลตามจริง ซึ่งอาจเป็น `schedules: []` เมื่อมีแต่ข้อมูล `TEST_` ใน Sheets; เฟิร์มแวร์ S3 **ต้องยอมรับตารางว่างที่ได้รับการยืนยันถูกต้อง** และลบตารางเก่าที่หมดสิทธิ์ ไม่ใช่ใช้แคชเก่าตลอดไป
- ยาทุก 8 ชั่วโมงนับจากเวลา **กดยืนยันครั้งแรกจริง** ยังไม่พร้อมทั้ง backend และ firmware; ห้ามระบุว่าเป็นฟังก์ชันที่ใช้งานได้แล้ว
- ต้องยืนยันการส่งข้อมูลภาพจาก ESP32-CAM ไป Google Drive จริงและตรวจสิทธิ์ของผู้ดูแล
